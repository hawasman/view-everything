# The Index stores names once, children as id runs, and only unpredictable sizes and times

ADR-0001 budgeted about 100 bytes per Entry. A background service cannot spend that: on a real Index of 5.6M Entries (530k folders) the loaded Index took 424 MiB, 43 bytes of fixed columns per Entry plus 132 MiB of names and about 45 MiB of one `Vec<EntryId>` per folder. Format 7 brings the same Index to 211 MiB, saves in 208 MB instead of 470 MB and loads in 0.24 s instead of 0.72 s, by storing less rather than compressing:

- **Names are interned.** 5.6M Entries used 1.8M distinct names (`index.js`, `.gitignore`, `mod.rs`...): 71 MiB of distinct names plus a 4-byte name number per Entry, instead of 132 MiB of names plus 6 bytes of start and length. The lookup table that interning needs (hashbrown's `HashTable`, about 10 MiB) exists only while inserting: `Index::idle` drops it when a sync ends, and the first insert after that rebuilds it.
- **Children are a run of ids.** A saved Index numbers Entries depth-first, so after a load every folder's children are consecutive ids: a first id and a count per folder (8 bytes) replace a `Vec` per folder. Entries renamed away or removed are skipped by checking their parent and removed flag while iterating the run. A child added later whose id does not follow the run is kept in a side list until the next save renumbers everything. A fresh scan inserts a folder's children one after another under one lock, so its runs form directly; an NTFS MFT read inserts in record order and lands in side lists until the first save. `Index::children` is therefore an iterator, not a slice.
- **A folder's slot is its rank.** Slots were assigned in id order among folders, which is exactly the count of folder bits below the id: a bitset with a running count every 512 rows (0.9 MiB) replaces a 4-byte slot per Entry.
- **On-disk Size and creation time store only exceptions.** 99.97% of Entries had On-disk Size equal to Logical Size rounded up to 4 KiB (0 for folders), and 79% had a creation time equal to their modification time. Each column is a bitset of exceptions with the exceptions' values in row order. A change after loading goes to an overlay (a bit and a hash-map entry) so an exception can appear or vanish without moving every value after it; the save writes a compact column. A Volume where the prediction fails (compressed btrfs, resident NTFS files, Remotes whose On-disk Size equals Logical Size) stores a value per such Entry and is no worse than before.
- **Times are kept to the second**, modification time included, in the 4-byte `U64Column` ADR-0001's successor introduced for sizes. Nothing read the nanoseconds: the UI, CSV export and `dm:` filters work in days or seconds, and the hash cache's staleness check already allowed a second. Pre-1970 and post-2106 times go to the column's wide side table.
- **Keys** (inodes, MFT record numbers) use the same 4-byte column; none exceeded 32 bits on the measured Index.

Per Entry this is 4 (parent) + 4 (name) + 1 (flags) + 4 (Logical Size) + 4 (modified) + 4 (key) + about 1.3 bits-and-exceptions = about 22 bytes, plus the distinct names.

What was not done: memory-mapping the saved file. The Index is mutated by every sync and live update, so a mapping would need a copy-on-write overlay, and once a search or sync has touched every page the resident size is the same as loading it.

A format 5 or 6 file is converted on load, once, row by row; the conversion needs the old and new columns at the same time and peaked at 260 MiB on the measured Index. Formats below 5 still ask for a rebuild.
